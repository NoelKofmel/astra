# Operations

How Astra runs in production: one Hetzner server, Docker Compose, deployed by
GitHub Actions. Everything here exists as code — `infra/` and
`.github/workflows/ci.yml` — so this document explains the steps a human has
to take, and why.

## The moving parts

```
git push main
  └─ CI/CD ─ check ─ images ─────────────── deploy ────────────── verify
             lint     web + worker → GHCR    scp infra files        GET /api/health
             types                           ssh deploy.sh <sha>    version == sha
             tests                             pull, migrate,
             build                             up --wait, rollback
```

On the server:

```
/opt/astra/
├── .env                  settings and secrets — generated by cloud-init, chmod 600
├── release.env           the release that is running, written by deploy.sh
├── docker-compose.yml  ┐
├── deploy.sh           │ copied from infra/ by every deploy
├── backup.sh           │
└── caddy/Caddyfile     ┘
/var/backups/astra/astra.dump    the latest database dump
```

Two users: `noel` for administration (sudo) and `deploy` for the pipeline and
the nightly backup (docker group, no sudo). **The docker group is
root-equivalent** — treat the CI deploy key like a root key.

## First setup

Done once. Allow an evening.

### 1. Keys

Your personal key already exists (`~/.ssh/id_ed25519.pub`). Create a second
one for GitHub Actions only, so it can be revoked without locking you out:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/astra-deploy -C astra-ci -N ""
```

### 2. Create the server

Hetzner Console → *Add Server*:

- **Location** Nuremberg or Falkenstein · **Image** Ubuntu 24.04 · **Type**
  CX32, or its current equivalent with 4 vCPU / 8 GB · **Name** `astra`
- **Firewall:** create one that allows inbound TCP 22, 80, 443 and UDP 443.
  UFW runs on the server as well, but Docker-published ports bypass UFW; the
  Hetzner firewall sits in front of everything.
- **Cloud config:** paste `infra/server/cloud-init.yaml` after replacing:
  - `REPLACE_WITH_YOUR_PUBLIC_KEY` — the content of `~/.ssh/id_ed25519.pub`
  - `REPLACE_WITH_CI_DEPLOY_PUBLIC_KEY` — the content of `~/.ssh/astra-deploy.pub`
  - `REPLACE_WITH_YOUR_EMAIL` — for Let's Encrypt expiry notices

The server installs, hardens and reboots itself — about five minutes.

### 3. First login and checks

```bash
ssh noel@<ipv4>                 # confirm the host key fingerprint once
cloud-init status --long        # status: done, no errors
sudo ufw status verbose         # 22 (limit), 80, 443
systemctl is-active docker fail2ban
ssh root@<ipv4>                 # must be refused
```

### 4. The server's `.env`

cloud-init generated `POSTGRES_PASSWORD` and `RESTIC_PASSWORD`.

```bash
sudo -e /opt/astra/.env
```

- **Copy `RESTIC_PASSWORD` into your password manager now.** The backups are
  encrypted with it; if the server is lost, so is every backup without it.
- `ASTRA_DOMAIN` stays `:80` (plain HTTP on the IP) until DNS is in place
  (step 7).

### 5. GitHub

Repository → *Settings*:

- *Environments* → create `production` (optionally: require your approval).
- *Secrets and variables → Actions → Secrets*:
  - `DEPLOY_HOST` — the server's IPv4
  - `DEPLOY_SSH_KEY` — the **private** key, `cat ~/.ssh/astra-deploy`
  - `DEPLOY_KNOWN_HOSTS` — `ssh-keygen -F <ipv4>` prints the line your first
    login verified; paste it without the comment line
- *Variables*: `ASTRA_URL` = `http://<ipv4>` for now. **Setting it switches
  deploys on**; without it, `main` only builds images.

### 6. First deploy

Merge to `main`. The pipeline checks, builds both images into GHCR, deploys
and verifies that `/api/health` reports the new commit. By hand:

```bash
curl http://<ipv4>/api/health    # {"ok":true,"version":"<sha>",...}
```

### 7. Domain and TLS

1. DNS: an `A` record to the IPv4, an `AAAA` record to the IPv6.
2. On the server, set `ASTRA_DOMAIN=<domain>` in `.env`, then recreate Caddy:
   `sudo -iu deploy`, `dc up -d caddy`. It fetches the certificate itself.
3. Set the GitHub variable `ASTRA_URL` to `https://<domain>`.

### 8. Backups

The timer runs every night at 03:30 UTC and fails visibly until this is done.

1. Order a Hetzner **Storage Box** (the smallest is plenty), enable *SSH
   support*, and enable **automatic snapshots** — they protect the backups
   even from someone who controls the server.
2. As `deploy`, give the server access (the box's SSH port is 23):

   ```bash
   sudo -iu deploy
   ssh-keygen -t ed25519 -f ~/.ssh/storagebox -N ""
   cat ~/.ssh/storagebox.pub | ssh -p 23 <user>@<user>.your-storagebox.de install-ssh-key
   cat >> ~/.ssh/config <<EOF
   Host storagebox
     HostName <user>.your-storagebox.de
     User <user>
     Port 23
     IdentityFile ~/.ssh/storagebox
   EOF
   ```

3. Create the repository and run a first backup:

   ```bash
   set -a; . /opt/astra/.env; set +a
   restic init
   exit
   sudo systemctl start astra-backup.service
   journalctl -u astra-backup -n 20          # "backup stored: …"
   systemctl list-timers astra-backup.timer
   ```

## Deploying and rolling back

Every push to `main` deploys. `deploy.sh` pulls the images, runs the
migrations while the old release keeps serving, starts the new release and
waits for its health checks. If it does not come up healthy, the previous
release is started again and the pipeline fails.

Manual rollback to an earlier commit, as `deploy`:

```bash
bash /opt/astra/deploy.sh <older-sha>
```

`deploy.sh` keeps a week of old images. For anything older the server has
to pull from GHCR, which needs `docker login ghcr.io` with a personal access
token (`read:packages`) — the pipeline's own token expires with its run.

Migrations never undo themselves on rollback. That is why they must stay
additive (`CLAUDE.md`): the older release has to work against the newer
schema.

## Restore

Always into a scratch database first — never straight over production:

```bash
sudo -iu deploy
set -a; . /opt/astra/.env; set +a
restic snapshots --tag postgres
restic dump latest /var/backups/astra/astra.dump > /tmp/astra.dump   # or a snapshot ID

dc exec -T postgres createdb -U astra astra_restore
dc exec -T postgres pg_restore -U astra -d astra_restore < /tmp/astra.dump
dc exec -T postgres psql -U astra -d astra_restore -c 'select count(*) from stories'
```

To replace production with it: `dc stop web worker`, drop and recreate the
`astra` database, `pg_restore` into it, `dc start web worker`. A scheduled
restore test is part of phase 8.

## Day to day

As `deploy` (`sudo -iu deploy`), `dc` is `docker compose` for the running
release:

| Task | Command |
|---|---|
| What runs, and is it healthy | `dc ps` |
| Logs | `dc logs -f --since 10m worker` |
| Health from outside | `curl https://<domain>/api/health` |
| Recent jobs | `dc exec postgres psql -U astra -c 'select job_name, status, started_at from job_runs order by id desc limit 10'` |
| Last backup | `journalctl -u astra-backup -n 5` |

Security updates install themselves; the server reboots at 04:30 UTC when a
kernel update needs it, and the containers come back on their own. Docker
itself is updated by hand: `sudo apt upgrade` now and then — `live-restore`
keeps the containers running while the daemon restarts.
